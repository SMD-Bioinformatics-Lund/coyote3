# Variant blacklist records

The `blacklist` collection stores one document per canonical allele identity,
not one per chromosome position or per assay group. Different reference or
alternate alleles at the same coordinate remain distinct records.

```json
{
  "simple_id": "7_100_A_T",
  "simple_id_hash": "666b4e86991008843943a5e5b5118ae0",
  "chrom": "7",
  "pos": 100,
  "ref": "A",
  "alt": "T",
  "assay_groups": ["hematology", "solid"],
  "in_normal_perc": {
    "hema_gmsv1": 0.2,
    "solid_gmsv3": 0.05
  }
}
```

`pos` is the positive, one-based genomic coordinate. The previous combined `pos`
string becomes `simple_id`. Chromosomes and alleles follow canonical variant
identity normalization. Group identifiers and assay dictionary keys are lowercase.
`simple_id_hash` is the lowercase MD5 digest of the canonical `simple_id`, using
the same function as the variants collection. It is generated by blacklist creation
and export conversion, and validated against `simple_id` by the collection contract.
`in_normal_perc` retains finite, nonnegative numeric values up to 100 without
rescaling them. Verify each source assay's measurement units before combining
exports; the converter does not infer whether a historical value used a fraction
or percentage scale.

An exclusion applies to every assay in a listed biological group. When loading
a finding, only the exact sample assay's measurement is used. A missing measurement
or a measured zero does not cancel the exclusion. Manual additions add the group
without inventing a normal-sample frequency or overwriting existing measurements.
Repeated additions are idempotent. A unique `simple_id` index prevents duplicate
allele records; concurrent group additions use an atomic set union.

## Prepare existing exports

Convert existing data before deploying the new schema and its unique index.
The converter accepts a newline-delimited Extended JSON export from v2, v3 or
the previous application blacklist. It reads and writes files only.

For old scalar frequencies, provide an explicit mapping from each source scope
to its biological group and physical assay. Use an assay ID only when the source
evidence establishes that ownership. If a scalar was measured for a whole group,
use an explicit `null` assay ID: the measurement remains in the source-evidence
file and is not assigned to a physical assay.

Example private `blacklist-scopes.json`:

```json
{
  "hematology": {"assay_group": "hematology", "asp_id": "hema_gmsv1"},
  "solid": {"assay_group": "solid", "asp_id": null}
}
```

```bash
.venv/bin/python migrations_scripts/prepare_blacklist.py \
  --input /secure/migration/blacklist-source.ndjson \
  --scope-map /secure/migration/blacklist-scopes.json \
  --output /secure/migration/blacklist-prepared.ndjson
```

Combine source exports into one input before preparing the final shared collection.
The tool merges groups for identical alleles, retains the first source ObjectId,
and rejects conflicting frequencies for the same allele and assay. Matching actor
values are retained; conflicting or absent actors remain null. The accompanying
`blacklist-prepared.sources.ndjson` retains every original document, including
its identifiers, authors and dates. Keep that file as private migration evidence;
do not import it into the application collection.

Review the prepared records and evidence, then import into an empty blacklist
collection in the approved separate destination:

```bash
mongoimport --uri "$TARGET_MONGO_URI" --db "$TARGET_MONGO_DB" \
  --collection blacklist --mode insert --stopOnError \
  --file /secure/migration/blacklist-prepared.ndjson
```

For an existing application deployment, keep it offline, retain a protected backup
of the original collection and its indexes, and validate the converted collection
before switching it into service. Do not mix old and new document shapes or use
upsert to conceal unresolved identity conflicts. The new runtime reads only the
documented schema.
