# Schema Contracts And Versioning

Coyote3 enforces collection contracts through domain-oriented Pydantic models.
All managed admin writes and ingest writes are contract-validated before persistence.

Managed-resource wiring lives in one registry:

- `api/contracts/managed_resources.py`

## Contract package layout

DB contracts are organized in `api/contracts/schemas/`:

- `base.py`: shared permissive base (`extra="allow"`) and version-history entry model.
- `samples.py`: sample document model and DNA/RNA key-consistency rules.
- `dna.py`: variants, CNVs, translocations, biomarkers, coverage-related models.
- `rna.py`: fusions, RNA expression/classification/QC models.
- `assay.py`: ASP/ASPC/ISGL and assay-linked blacklist models.
- `governance.py`: users, roles, permissions, schema-definition documents.
- `reference.py`: annotation knowledgebase and annotation contracts.
- `registry.py`: collection-to-model adapter map and validation helpers.

## Single source mapping

`api/contracts/managed_resources.py` is the single source that links:

- admin resource key (for example `role`, `user`, `asp`, `aspc_dna`)
- target Mongo collection contract (for example `roles`, `users`, `asp_configs`)
- contract-owned UI schema identity (`schema_type`, `schema_category`, `schema_id`)

Managed resources currently covered end-to-end:

- ASP (`assay_specific_panels`)
- ASPC DNA (`asp_configs`)
- ASPC RNA (`asp_configs`)
- ISGL (`insilico_genelists`)
- Users (`users`)
- Roles (`roles`)
- Permissions (`permissions`)

## Write-path enforcement

Create/update flows validate and normalize payloads against contracts before DB writes:

- Internal ingest collection endpoints (`/api/v1/internal/ingest/collection*`)
- Admin create/update for:
  - ASP (`assay_specific_panels`)
  - ASPC (`asp_configs`)
  - ISGL (`insilico_genelists`)
  - Users (`users`)
  - Roles (`roles`)
  - Permissions (`permissions`)

Contract ownership for ingestion is explicit:

- sample file-key groups (`DNA_SAMPLE_FILE_KEYS`, `RNA_SAMPLE_FILE_KEYS`, `SAMPLE_SOURCE_PATH_KEYS`) are defined in `api/contracts/schemas/samples.py`
- dependent ingest collection bindings are defined in `api/contracts/schemas/registry.py`
- ingest service consumes those contract-owned constants and writes normalized documents only

## Admin form and contract catalog source

For managed admin resources (`asp`, `aspc`, `isgl`, `users`, `roles`, `permissions`),
UI form schema payloads are generated by backend code from Pydantic contracts and
managed-resource mapping.

- Mapping: `api/contracts/managed_resources.py`
- Generated UI schema: `api/contracts/managed_ui_schemas.py`

UI form definitions for these resources are backend-owned and generated from contracts.

Generated payloads include UI-ready structure:

- `fields` with `data_type`, `display_type`, `required`, `default`, and `options`
- ordered `sections` used directly by admin templates
- system metadata fields (`created_by`, `created_on`, `updated_by`, `updated_on`, `version`)
- resource-specific field behavior (for example gene upload/edit fields and JSON editors)

Operational flow:

1. UI requests `create_context` from API.
2. API builds schema from managed contracts.
3. UI renders fields from returned `sections` + `fields`.
4. UI submits form payload only.
5. API services stamp `version` and `version_history`.
6. API validates payload with collection contract and writes to Mongo.

This keeps UI schema behavior and DB-write validation in one backend source of truth.

## Admin Resource Versioning Model

Coyote3 uses two versioning patterns because clinical configuration and access
governance have different operational requirements.

### Clinical configuration: active-version rotation

Clinical configuration resources are append-only at the active document level.
Editing one of these resources creates a new active document and retires the
previous active document:

- ASP (`assay_specific_panels`)
- ASPC (`asp_configs`)
- ISGL (`insilico_genelists`)

The user-facing business key stays stable (`asp_id`, `aspc_id`, or `isgl_id`).
The MongoDB `_id` changes because the edited resource is a new versioned
document. The retired document keeps its previous content and receives:

- `is_active: false`
- `retired_by`
- `retired_on`
- `retired_reason`
- updated metadata for audit traceability

Runtime reads resolve active documents by default. MongoDB enforces one active
document per business key with partial unique indexes on `(business_key,
is_active)` where `is_active` is `true`.

This model is required for clinical reproducibility. A sample or report can be
linked to the exact ASPC/ISGL/ASP version that was active when the analysis or
report snapshot was produced.

### Identity and access governance: in-place version increments

Operational access resources update in place and increment `version`:

- Users (`users`)
- Roles (`roles`)
- Permissions (`permissions`)

These resources must remain easy to migrate, hydrate into RBAC policy, and query
by their unique identity. A role or permission edit does not create another
document with the same business key. Instead, the existing document is updated
with:

- incremented `version`
- appended `version_history`
- updated `updated_by` and `updated_on`
- audit-log event through the mutation/audit path

MongoDB enforces one document per `role_id` and one document per
`permission_id`. User documents are unique by their object identity plus unique
username/email constraints.

This keeps the current access model deterministic while preserving traceability
through version metadata and audit events. Historical RBAC replay, if needed for
security investigations, should be reconstructed from audit entries rather than
from inactive duplicate role/permission documents.

## Contract catalog UI

The Admin Contract Catalog is an inspection surface over the active backend contracts.
It is not an editor and it does not write to a MongoDB `schemas` collection.

The page displays:

- collection name and model title
- required fields
- field names exposed by the active Pydantic JSON schema

Resource creation and editing must happen through the dedicated managed-resource
forms. This keeps clinical configuration changes inside the same validation,
permission, audit, and versioning flow used by all admin writes.

## Versioning and stability

- Keep `version` increments on updates.
- Keep `version_history` entries on create/update mutations.
- Apply explicit contract changes and maintain strict write-path validation.
- Use strict contracts where key-level lock is required (`_StrictDocBase`).

## Recommended evolution pattern

1. Add/adjust Pydantic fields in `api/contracts/schemas/*`.
2. If form behavior changes, update resource UI metadata in `api/contracts/managed_ui_schemas.py` (sections/display types/overrides).
3. Bump managed contract version in `api/contracts/managed_resources.py` when version semantics change.
4. Update seed fixtures with new keys (`tests/fixtures/db_dummy/*`) when baseline data changes.
5. Update docs generated from contracts (`scripts/export_collection_contracts_doc.py`) and relevant developer/product pages.
6. Add/update tests in `tests/unit/test_db_documents.py` and admin-service tests.
7. Run `bash scripts/check_contract_integrity.sh` before merge.
8. For breaking key changes, add migration script and guide entry.
